# AI 旅行决策助手：整体与详细说明

## 一、项目定位

这个项目不是在线旅行社，也不负责订票。它是一套可运行的 LangChain 1.2 教学案例：把用户的自然语言需求拆成多个可验证的小任务，让大模型决定工具调用顺序，再由 Python 完成确定性计算和外部天气查询。

适合已学习模型初始化、消息、提示词、结构化参数和 Tools 的学习者。项目有意停留在“Tools + 手写循环”的层级，便于看清 Agent 底层最关键的工作过程。

## 二、整体流程

一次完整提问会经历以下过程：

```text
用户中文需求
    ↓
系统提示词约束模型
    ↓
模型产生一个或多个 tool_calls
    ↓
TravelAssistant 按名称找到 Python 工具
    ↓
工具返回 JSON 字符串，包装成 ToolMessage
    ↓
模型读取工具结果，决定继续调用工具或生成最终答案
    ↓
CLI 展示工具轨迹和中文旅行建议
```

例如“杭州到上海三天两人舒适游，总预算 3000 元”并不是一次简单问答。合理的调用链可能是：

```text
plan_trip_dates
    ├─ search_transport
    ├─ estimate_hotel_cost
    ├─ estimate_food_cost
    └─ search_attractions
             ↓
calculate_total_budget
             ↓
最终方案
```

前四类费用互不依赖时，支持同一轮并行提出多个工具调用；总预算必须等待各项费用产生后再调用，因此通常发生在下一轮。

## 三、各文件职责

### `main.py`

命令行入口。负责参数解析、交互命令、加载设置、创建助手、显示工具轨迹和最终答案。它不包含旅行计算规则，以便界面层和业务层分离。

### `travel_assistant/config.py`

使用 `python-dotenv` 读取项目根目录 `.env`，再完成以下校验：

- provider 只能是 `deepseek` 或 `ollama`。
- DeepSeek 必须提供 API Key。
- Ollama 缺省地址为 `http://localhost:11434`。
- 最大工具轮数必须在 1 到 20 之间。
- 将 `true/false` 等文本转换为布尔值。

设置使用不可变的 `dataclass`，避免运行过程中意外改写配置。

### `travel_assistant/prompts.py`

系统提示词定义助手的行为边界。最重要的约束是：

- 实时信息必须调用工具，不能编造。
- 必须区分实时天气和教学估算。
- 完整预算必须调用 `calculate_total_budget`，避免语言模型心算。
- 工具失败时应诚实报告。
- 最终答案需要提供决策依据和风险提示。

### `travel_assistant/data.py`

读取并缓存 `data/destinations.json`；把“上海市”规范化为“上海”；使用 Haversine 公式根据经纬度计算两座城市的直线距离。

`@lru_cache(maxsize=1)` 让城市数据在一次程序运行中只读取一次。

### `travel_assistant/tools.py`

定义 Pydantic 入参和 8 个带 `@tool` 的函数。工具统一返回 JSON 字符串，因为 JSON 既方便模型理解，也便于测试验证字段。

### `travel_assistant/assistant.py`

这是项目核心。它包含模型初始化和手写工具循环：

1. `bind_tools(TOOLS)` 把工具名称、说明和参数模式交给模型。
2. 把用户问题作为 `HumanMessage` 加入消息历史。
3. 调用绑定工具后的模型。
4. 若返回的 `AIMessage.tool_calls` 为空，就结束并显示文本答案。
5. 若存在调用，就根据名称从 `TOOL_MAP` 找到工具并执行。
6. 把执行结果作为 `ToolMessage` 加入历史，再次调用模型。
7. 超过最大轮数就主动停止，防止错误模型无限循环。

异常会被转换为工具失败消息，而不是让整个会话直接崩溃。

## 四、8 个工具详解

### 1. `plan_trip_dates`

输入起止日期和人数，输出旅行天数、住宿晚数和人数。当天往返是 1 天、0 晚；教学项目限制最长 31 天。

### 2. `search_transport`

输入出发城市、目的城市、日期、人数、单程/往返和交通方式。它先计算直线距离，再使用教学系数估算高铁距离、公路距离、耗时和总票价。

自驾选项不会直接给出总价格，而会返回 `requires_next_tool=calculate_driving_cost`，提示模型继续使用更合适的专用工具。

### 3. `calculate_driving_cost`

核心公式：

```text
总里程 = 单程里程 × 单程/往返系数
耗油量 = 总里程 × 百公里油耗 ÷ 100
油费 = 耗油量 × 油价
过路费 = 总里程 × 每公里过路费
车辆总成本 = 油费 + 过路费 + 停车费
人均成本 = 车辆总成本 ÷ 人数
```

车辆折旧、保险和实时拥堵未计入。

### 4. `estimate_hotel_cost`

根据城市价格基准、档次、晚数和房间数计算：

```text
住宿总价 = 每间每晚基准价 × 晚数 × 房间数
```

档次包括 `economy`、`comfort`、`premium` 和 `luxury`。

### 5. `estimate_food_cost`

根据城市、天数、人数和餐饮标准计算：

```text
餐饮总价 = 每人每日基准价 × 旅行天数 × 人数
```

标准包括 `budget`、`standard` 和 `premium`。

### 6. `search_attractions`

将用户兴趣与景点 `categories` 做交集匹配，返回最多指定数量的景点，并按人数汇总门票。当前使用简单的精确标签匹配，适合观察工具行为，也容易自行升级为语义检索。

### 7. `get_travel_weather`

这是唯一使用实时外部数据的工具：

1. 调用 Open-Meteo Geocoding API，把城市转换成经纬度。
2. 调用 Forecast API 查询每日天气。
3. 将 WMO 天气代码转换成中文描述。

它限制查询今天至未来 15 天，且每次最多连续 7 天。网络超时会重试 3 次；失败后返回错误 JSON，不会伪造天气。

### 8. `calculate_total_budget`

汇总交通、住宿、餐饮、门票、市内交通和其他必要费用，再增加预备金：

```text
小计 = 所有费用项之和
预备金 = 小计 × 预备金百分比
预计总额 = 小计 + 预备金
人均费用 = 预计总额 ÷ 人数
```

提供预算上限时，还会输出是否在预算内以及剩余/超出金额。

## 五、为什么工具比让模型直接回答更可靠

大模型适合理解“想轻松一点、喜欢历史、预算有限”这类模糊语言，但不应该负责精确日期差、费用公式或实时天气。项目把职责分开：

- 模型负责意图理解、参数提取、选择工具和组织答案。
- Pydantic 负责工具参数类型与范围校验。
- Python 函数负责确定性计算。
- 外部 API 负责提供天气事实。
- 系统提示词负责约束表达和数据质量说明。

这正是 Tool Calling 的核心价值：不是让模型“知道更多”，而是让它在需要事实或计算时使用受控能力。

## 六、从一次请求理解消息序列

假设用户问：

```text
2026-09-01 到 2026-09-03，我和朋友从杭州去上海，
住一间舒适型酒店，比较高铁和自驾，总预算 3000 元。
```

消息历史可能依次为：

```text
SystemMessage  系统规则
HumanMessage   用户需求
AIMessage      tool_calls: 日期、交通、酒店、餐饮、景点
ToolMessage    日期结果
ToolMessage    交通结果
ToolMessage    酒店结果
ToolMessage    餐饮结果
ToolMessage    景点结果
AIMessage      tool_calls: 自驾成本、总预算（实际可能分成两轮）
ToolMessage    自驾结果
ToolMessage    总预算结果
AIMessage      最终中文建议
```

工具调用 ID 很重要：每个 `ToolMessage` 必须通过 `tool_call_id` 对应模型之前发出的调用，否则许多模型服务会拒绝消息序列。

## 七、数据边界与安全策略

- `.env` 只保存在本机，`.gitignore` 明确排除它。
- 工具参数通过 Pydantic 设置人数、天数、金额等上下限。
- 最大工具轮数防止无限循环和意外消耗额度。
- 城市不在本地教学数据中时，费用工具明确失败。
- 远期或历史天气请求明确失败。
- 交通和消费结果始终标为估算，不冒充实时价格。
- 项目不执行预订、支付、发消息等外部写操作。

## 八、测试设计

测试分成三组：

- `test_config.py`：检查 DeepSeek 缺密钥、Ollama 默认地址和轮数范围。
- `test_tools.py`：检查日期、交通、自驾、住宿、餐饮、景点、天气和预算。
- `test_assistant.py`：用假模型产生真正的 `tool_calls`，确认程序执行工具、加入 `ToolMessage`，再获得最终答案。

假模型和模拟天气响应使测试完全离线，不使用真实密钥，也不消耗模型额度。

## 九、推荐代码阅读顺序

1. 先读 `main.py`，了解程序入口。
2. 再读 `config.py` 和 `.env.example`，理解配置加载。
3. 阅读 `tools.py` 中最简单的 `plan_trip_dates`。
4. 对比 Pydantic 输入模型、`@tool` 和返回 JSON。
5. 阅读 `assistant.py` 的 `ask()`，逐行跟踪消息循环。
6. 阅读 `test_assistant.py`，理解假模型如何模拟 Tool Calling。
7. 最后修改 `destinations.json` 或新增工具，再运行测试。

## 十、练习与扩展路线

### 初级练习

- 新增重庆、武汉或长沙数据。
- 为景点增加闭馆日字段。
- 增加儿童人数和儿童票价。
- 增加“青旅”住宿档次。

### 中级练习

- 加入人民币之外的币种和汇率工具。
- 用真实地图 API 替代 Haversine 距离估算。
- 把精确兴趣标签升级成向量语义检索。
- 用结构化输出生成稳定的旅行方案对象。

### 学完 Agent 后

- 用 LangChain Agent 重写工具循环，对比代码量与可控性。
- 加入检查点和持久化记忆，让会话可恢复。
- 增加行程审核 Agent，检查时间冲突和预算遗漏。
- 使用 LangSmith 评估工具选择准确率、预算完整率和失败恢复能力。

### 做成完整应用

- 使用 FastAPI 提供后端接口。
- 使用 Streamlit 或前端框架制作表单与预算图。
- 建立用户收藏、历史方案和多人协作。
- 在具备授权和确认机制后，接入真实预订服务。

## 十一、调试方法

当结果不符合预期时，按这个顺序检查：

1. 打开 `SHOW_TOOL_TRACE=true`，确认模型调用了什么工具。
2. 用 `/clear` 排除旧对话条件干扰。
3. 把问题中的日期、人数、房间数和档次写明确。
4. 单独在 Python 中调用对应工具，区分“工具计算错”和“模型选错工具”。
5. 执行 `python -m pytest` 确认基础行为没有回归。
6. 若是在线模型问题，再检查 Base URL、模型名、额度和网络。

这个排查顺序体现了一个重要工程原则：先验证确定性的本地组件，再排查不确定的模型行为和外部服务。
